# Hiring Intelligence AI

## Project Development Process

### Overview

Hiring Intelligence AI is an AI-powered recruitment analytics platform that enables users to analyse hiring data using natural language instead of SQL queries.

The primary objective of this project was **not simply to integrate an LLM**, but to build a reliable analytics system where Artificial Intelligence understands the user's intent while the application itself performs all business logic in a deterministic and secure manner.

The application follows a modular architecture consisting of authentication, authorization, AI query understanding, validation, analytics execution and dashboard visualization.

---

# 1. Engineering Approach

Instead of asking the Large Language Model to answer hiring questions directly, the application separates the responsibilities into independent layers.

```
User Question
        │
        ▼
Gemini 2.5 Flash
(Intent Understanding)
        │
        ▼
Query IR
        │
        ▼
Validation
        │
        ▼
Analytics Engine
        │
        ▼
CSV Dataset
        │
        ▼
Final Response
```

This separation ensures that business calculations are never performed by the LLM.

---

# 2. Assumptions

During development the following assumptions were made.

- CSV datasets are considered the source of truth.
- Users must authenticate before accessing analytics.
- Every analytics request passes through server-side authorization.
- Gemini generates only Query IR.
- The analytics engine performs every calculation.
- Invalid Query IR is rejected before execution.
- Dashboard metrics should also respect role permissions.

---

# 3. Why Query IR?

One of the most important architectural decisions was introducing an Intermediate Representation (Query IR).

Instead of asking Gemini to produce answers directly, the model converts natural language into structured JSON.

Example

User asks

```
Count AI jobs
```

Gemini returns

```json
{
  "entity": "jobs",
  "metric": "count",
  "filters": [
    {
      "field": "department",
      "operator": "=",
      "value": "AI"
    }
  ]
}
```

The analytics engine executes this JSON against structured datasets.

### Advantages

- Eliminates hallucinated analytics
- Easy to validate
- Easy to debug
- Independent from the LLM
- Deterministic execution
- Simple to extend

---

# 4. Provider Abstraction

The application was intentionally designed with a provider abstraction layer.

Instead of calling Gemini directly throughout the project, every request goes through a common provider interface.

Benefits

- Easily replace Gemini with OpenAI
- Easily replace Gemini with Claude
- Business logic remains unchanged
- Cleaner architecture

This keeps the AI layer independent from the rest of the application.

---

# 5. Prompt Engineering

Prompt engineering was one of the most iterative parts of the project.

Initially the LLM occasionally produced:

- Markdown wrapped JSON
- Incorrect field names
- Missing attributes
- Incorrect filters

To improve reliability:

- Added strict prompt instructions.
- Added dataset schema.
- Added Query IR examples.
- Forced JSON-only output.
- Restricted allowed metrics.
- Restricted allowed entities.

This significantly improved structured output consistency.

---

# 6. Validation Strategy

Although Gemini generally produced valid JSON, malformed outputs occasionally occurred.

To prevent runtime failures, every Query IR passes through Zod validation before execution.

Validation checks

- Required fields
- Filter structure
- Entity
- Metric
- Operators

Invalid queries are rejected immediately.

This prevents invalid analytics execution.

The final analytics response is also validated using Zod before being returned to the frontend, ensuring consistent API contracts and preventing malformed responses.
---

# 7. Grounded Responses

To improve explainability, every analytics response includes grounding metadata.

Grounding contains:

- Dataset used
- Number of matched rows
- Fields used
- Applied filters

This allows users to understand how a response was produced instead of treating the AI as a black box.

Grounding is generated by the analytics engine after execution and returned together with the response.
---

# 8. Analytics Engine Design

The analytics engine is completely independent of Gemini.

Execution pipeline

```
Dataset Loader

↓

Role Scope

↓

Filters

↓

Sorting

↓

Grouping

↓

Aggregation

↓

Response Builder
```

Each module has only one responsibility.

Advantages

- Modular
- Testable
- Reusable
- Easy to maintain

---

# 9. Authentication & Authorization

Authentication is implemented using NextAuth.

Passwords are hashed using bcrypt before storage.

After login:

- JWT Session is created.
- User role is attached to the session.
- Every analytics request validates the session.

Supported roles

- ADMIN
- HR
- RECRUITER

Authorization is enforced on the server before analytics execution.

This ensures unauthorized users cannot access restricted hiring information.

# 12. Challenges Faced

## 1. Gemini JSON Formatting

Initially Gemini returned markdown wrapped JSON.

Solution

Improved prompt engineering and implemented JSON parsing.

---

## 2. Invalid Query Structures

Some generated IR objects contained missing fields.

Solution

Introduced Zod validation before execution.

---

## 3. Small Dataset

The original sample dataset contained only a few records.

Solution

Expanded the dataset to 128 realistic hiring records covering multiple departments, recruiters, locations and job roles.

---

## 4. Role-Based Dashboard

Initially dashboard metrics ignored user roles.

Solution

Implemented server-side role filtering before computing dashboard statistics.

---

## 5. Authentication

Integrating Prisma with NextAuth required mapping application roles with Prisma enum values.

Solution

Updated authentication callbacks and standardized role names.

# 17. Conclusion

The project demonstrates how Large Language Models can be integrated into enterprise analytics while maintaining security, determinism and modularity.

Instead of allowing the LLM to generate business answers directly, the application separates intent understanding from execution through Query IR and a deterministic analytics engine.

This architecture improves reliability, explainability, maintainability, and security by separating natural language understanding from deterministic analytics execution and providing grounded responses.
